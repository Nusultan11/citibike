# BikeFlow Intelligence — инструкции Codex

## Назначение и источники

BikeFlow Intelligence — аналитическая и прогнозно-рекомендательная платформа
городского велопроката; исходные документы используют название CitiBike Intelligence Platform.
Факты, прогнозы и сценарные рекомендации должны быть различимы и проверяемы.

Текущая задача определяет разрешённый объём; эти инструкции — порядок работы.
Документы дополняют друг друга по назначению:
- [PROJECT_SPEC.md](PROJECT_SPEC.md) — продукт, требования и границы выпуска.
- [ARCHITECTURE.md](ARCHITECTURE.md) — устройство, стек и архитектурные ограничения.
- [DATA_CONTRACTS.md](DATA_CONTRACTS.md) — контракты данных и совместимость.
- [METRICS.md](METRICS.md) — определения и формулы метрик.
- [ML_SPEC.md](ML_SPEC.md) — признаки, обучение и оценка моделей.
- [OPERATIONS.md](OPERATIONS.md) — проверки, release gates, защита и восстановление.
- [ROADMAP.md](ROADMAP.md) — последовательность, критерии этапов и единый журнал (§6).
- [knowledge_base/](knowledge_base/) — вспомогательные материалы, не замена контрактам.

При противоречии или недоступном обязательном источнике сообщить о проблеме;
не выдумывать требования. Читать только контекст текущего подшага.

## Этапность и полномочия

F0 Foundation → F1 First End-to-End → F2 Data Trust → F3 Analytics →
F4 Forecasting → F5 Risk & Optimization → F6 Product → F7 Automation →
F8 Production Hardening. Зависимости и допустимое пересечение — только по ROADMAP.
Выполнение подшага не означает завершения фазы: проверять её полный DoD.
F0.1 ограничен документацией и настройкой работы Codex; приложение здесь не создавать.

Для одного утверждённого подшага использовать
[bikeflow-step](.agents/skills/bikeflow-step/SKILL.md).
Не начинать следующий подшаг без приёмки пользователя.

## Рабочий цикл

1. Прочитать корневые и применимые вложенные AGENTS.md; проверить ветку, HEAD,
   remote, Git status и существующие изменения. Не затирать чужую работу.
2. Сопоставить журнал с кодом, тестами и конфигурацией; определить границы и DoD
   одного согласованного подшага, затем прочитать необходимые контракты.
3. Сделать минимальное проверяемое изменение по существующим паттернам.
   Не менять несвязанные файлы, не добавлять зависимости или инфраструктуру без нужды.
   Сохранять рабочее поведение; изменения контрактов сопровождать миграцией и тестами.
4. Обрабатывать ошибки явно. Для исправления дефекта: воспроизведение → причина →
   минимальная правка → регрессионный тест → проверка. Применённые миграции не переписывать.
5. Выполнить целевые тесты и применимые проверки OPERATIONS, включая негативные
   и аварийные сценарии по риску; после исправлений повторить затронутые проверки.
   Для документационного подшага проверять целостность, ссылки и формат без каркаса приложения.
6. Обновить только журнал ROADMAP §6: дата, этап/подшаг, статус, сделанное,
   подтверждённые команды/результаты, SHA/PR, ограничения/выводы, один следующий шаг.
7. Просмотреть итоговый diff, staged files, секреты и Git status. После проверенного
   подшага создать целевой Conventional Commit; указать его SHA в журнале отдельным
   минимальным коммитом, если нужно. Push в origin — при разрешении и доступе.
8. Подготовить фактический отчёт и остановиться. При блокере остановить зависимую
   часть; допустимую независимую работу завершить и явно указать остаток.

## Достоверность, безопасность и чистота

Не выдавать предложенное за реализованное, формат ответа — за правильность расчёта,
цели производительности — за измерения. Не выдумывать команды, результаты и метрики.
Для data/ML соблюдать provenance, train/test isolation, as-of правила и воспроизводимый
baseline; оценивать качество, задержку и ресурсы, указывать неудачные наблюдения.
Секреты — в env/secret storage; не включать их в файлы, коммиты и логи.
Не коммитить raw datasets, модели и тяжёлые генерируемые артефакты.
Не создавать параллельные журналы и копии с суффиксами v1/v2/final/new/backup/old/copy.
История изменений — Git; запрещены force push, удаление истории, reset/clean чужой работы.
Бэкапы БД и ML-артефактов выполнять по OPERATIONS §6 в соответствующем подшаге.

## Отчёт о завершении

1. Статус подшага и фазы: COMPLETED / PARTIAL / BLOCKED по фактическому DoD.
2. Сделано: конкретный результат.
3. Не сделано: остаток и причины.
4. Файлы: созданные и изменённые пути.
5. Проверки: точные команды и результаты; пропуски — NOT VERIFIED с причиной.
6. Решения и выводы: отклонения, технический долг и найденные несвязанные проблемы.
7. Блокеры и риски.
8. Git: ветка, SHA, сообщения коммитов, точный итоговый status и статус push.
9. Следующий шаг: один ближайший подшаг по ROADMAP; автоматически его не выполнять.
