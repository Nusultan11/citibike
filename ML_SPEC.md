# ML_SPEC — задачи, эксперименты и inference

**Назначение:** единое техническое описание ML-решения. Бизнес-смысл — [PROJECT_SPEC.md](PROJECT_SPEC.md); метрики активности — [METRICS.md](METRICS.md); корректность временных данных — [DATA_CONTRACTS.md](DATA_CONTRACTS.md).

## 1. Основные задачи

**A. Departure forecasting** — прогноз числа **наблюдаемых опубликованных** отправлений на станции за каждый из 24 следующих часов.  
**B. Arrival forecasting** — прогноз числа завершений поездок на станции за те же часы.  
Обе задачи — прогнозирование счётных неотрицательных значений, возможны нули и малонагруженные станции.

**Уровень записи ML:** `(station_id, forecast_origin_utc, target_hour_utc, horizon_h, prediction_type)`; `target` известен только для обучающих/оценочных примеров. Forecast origin — фактическое время принятия прогноза. Для production целимся в ежедневный 24-часовой batch; отдельный GBFS-based оперативный контур рассматриваем после накопления истории.

## 2. Ограничение доступности информации

Обязателен **point-in-time join** по моменту доступности, не только по event timestamp:

- Архив поездок доступен лишь после его фактической публикации/скачивания. `lag_1h`, `lag_24h` из ещё не опубликованных поездок запрещены для production.
- Фактическую будущую погоду нельзя использовать как forecast feature. Нужен исторический weather forecast, доступный в момент origin, либо эксперимент без погоды.
- GBFS snapshot может использоваться лишь если он собран не позднее origin и ещё достаточно свеж; не подменять пробелы будущими снимками.
- Историческая ёмкость/статус станции — версия, существовавшая на момент прогноза.
- При отсутствии точных публикационных меток честно маркировать retrospective backtest как приближённый, а не точную production-симуляцию. Прежний proxy `publication_month_end + 45 days` — консервативное допущение исследования, не свидетельство фактического `available_at`.
- Для каждого источника/признака фиксировать `event_at`, `published_at`/`received_at` (если известны), `available_at`, происхождение, версию и допустимость на `forecast_origin_utc`. Неопределённый момент публикации не заменять временем события.
- Обнаруженные разрывы в city-hour, неоднозначные идентификаторы станций и невозможность восстановить исторический GBFS за прошлые годы — ограничения входов; они не исправляются фиктивными значениями.

## 3. Feature groups

| Группа | Примеры | Условие |
|---|---|---|
| Calendar | Час, день недели, месяц, выходной, праздник, DST | Известно заранее |
| Station | Станция, координаты, известная ёмкость, исторический профиль | Только as-of version |
| Demand profile | Долгосрочные сезонные распределения, lag по опубликованным месяцам | Доступность документа подтверждена |
| Weather | Температура/осадки/ветер из archived forecast | `forecast_issued_at ≤ origin` |
| GBFS | Текущее наличие, прошлые снимки, давность наблюдения | Coverage достаточен; snapshot ≤ origin |
| Station identity (P0) | Подтверждённое соответствие физических станций, глубина истории | Версионированный lineage as-of, без объединения raw/Silver и незаметного изменения target population |
| Cold start / reliability (P0) | Глубина и доля доступной истории, confidence профиля | Считаются только из опубликованной к origin истории; missing не равен 0 |
| Demand peaks (P0) | Историческая доля пиков, сглаженные верхние квантили и интенсивность | Train-only расчёты, защита редких станций; не дублировать имеющиеся профили |
| Spatial / source quality (P1) | Исторические соседние/маршрутные связи, возраст и покрытие источника | Исторические версии координат/маршрутов; признаки доступности не маскируют leakage |

Не делать сотни признаков до baseline. Для каждого feature хранить формулу, grain, тип, null semantics, source lineage, `available_at`, версию и проверки leakage/train–serve parity. Новые группы — только по зафиксированной гипотезе EDA, без изменения существующего Gold/Silver; пользу определять через отдельную ablation на одних и тех же validation folds. Weather/GBFS расширять только после подтверждённого as-of покрытия.

## 4. Экспериментальный план

| Порядок | Алгоритм | Зачем |
|---|---|---|
| 0 | Seasonal Naive | Контрольный уровень, обязателен |
| 1 | Poisson regression / простая статистическая модель | Интерпретируемая регрессия счётных значений |
| 2 | LightGBM | Основной сильный табличный кандидат |
| 3 | CatBoost | Сравнение обработки категорий и сложных связей |
| 4 | Hurdle | Отдельно оценить вероятность ненулевого спроса и интенсивность при положительном спросе |
| 5 | N-HiTS | Отложенная проверка DL только при доказанной потребности и бюджете |

Для обучаемых моделей: (A) frozen baseline/default и фиксированная population; (B) одна проверяемая гипотеза (identity, cold-start, peak, loss) и отдельная ablation; (C) ограниченный search параметров (Optuna только по необходимости); (D) stress-test финалистов. Не смешивать эффект признаков с tuning. До запуска зафиксировать source hashes, версии station mapping, folds/origins, search space, trials/time budget, seed, критерий остановки и CPU/RAM. Сохранять все trials, включая неудачные, и evidence о результате. Early stopping/selection — только на train/validation. Negative Binomial и quantile boosting допускаются при обнаруженной сверхдисперсии/потребности в интервалах; усложнение без устойчивого выигрыша прекращать.

Результат EDA/анализа ошибки переводится в проверяемую гипотезу: источник и доказательство → предполагаемая причина → допустимые признаки/метод → замороженное сравнение → `accepted for research` / `rejected` / `inconclusive`. Использовать существующий F4 research runner и его артефакты, не создавать отдельную платформу экспериментов. Пока отдельный promotion gate не пройден, operational champion — Seasonal Naive; исследовательские победители автоматически его не заменяют.

## 5. Валидация и метрики

- **Rolling-origin backtesting** со строгой временной последовательностью и публикационной задержкой. Train → несколько Validation окон → нетронутый final Test, исключая перекрывающиеся целевые интервалы.
- Основная метрика: **MAE** в поездках за station-hour. Дополнительные: WAPE при ненулевой сумме actual, RMSE, bias, peak-hour MAE.
- Отдельные разрезы: станции с низкой/высокой активностью, сезон, будни/выходные, горизонт 1–24 часа, новые станции, cold start, нулевые метки, пиковые факты (`actual ≥ 20` — только post-hoc), аномальные/пропущенные периоды и доступность источника. Отличать `DATA ERROR`, `MODEL ERROR`, `INFORMATION LIMITATION`. Анализировать residual/bias, sample coverage, вариацию между folds; происхождение origin (например, исключительно 00:00 UTC) учитывать при выводах о горизонте.
- Валидность output: число ≥0, конечное, с корректным origin/target; квантильные интервалы проверять на покрытие и порядок границ.
- В эксперименте фиксировать dataset checksum, source/alias lineage, feature schema/version, origin, seed, версии кода/библиотек, конфигурации, ресурсы, training/inference time, prediction/residual rows и результаты tuning. Для сравнения использовать парные строки и station×day block uncertainty/бустрэп с учётом зависимости и множественных сравнений. Ранее раскрытые H0–H3 и сентябрь 2026 не считать новым независимым тестом: новые решения требуют нового forward/shadow-периода.

**Promotion gate:** исследовательский лидер выбирается только по заранее замороженной validation-процедуре: повторяемый выигрыш над baseline на сопоставимой population, без критической деградации важных сегментов, с достаточным покрытием, valid features и допустимыми ресурсами. Operational champion дополнительно требует подтверждённой strict point-in-time доступности, train/serve parity, нового независимого forward/shadow-периода, ручного approval и работающего rollback. Недостаточное доказательство → сохранить Seasonal Naive или `unavailable`; не переключать active pointers из research.

**Диагностика аномалий (исследовательский ML-контур):** начать с контекстного baseline по station × локальным weekday/hour × season, проверки длительных нулей и CUSUM по очищенным от сезонности остаткам. PELT — только offline для исследования сдвигов; не заменять им онлайн-детекцию. Событие требует периода, `event_at`, `detected_at`, `available_at`, типа/score, качества источника, версии и evidence; соседние сигналы дедуплицировать. Проверять controlled injections, экспертную Precision@K, false alerts и detection delay; статистическая редкость не означает ошибку данных или закрытие станции.

## 6. Risk engine и оптимизация — отдельные компоненты

Сначала объединяем прогнозы отправлений/прибытий с валидными GBFS-снимками в симуляции запасов. Текущие независимые Poisson-события и масштабы сценариев дают **модельную долю** опустошений/переполнений, не калиброванную вероятность фактического скрытого спроса. Wilson CI характеризует Monte Carlo точность при заданных допущениях, но не валидность этих допущений. При необходимости проверять сверхдисперсию, quantile/pinball, coverage и калибровку распределений на независимых observed targets. Оптимизацию сравнивать с no-action и эвристикой на одних событиях по согласованному `simulated_loss + λ × scenario_cost`, с проверкой вместимости, времени и баланса. Текущий MILP может оптимизировать суррогат целевых остатков, поэтому его оптимум не гарантирует улучшение итоговой сценарной функции. Рекомендация допустима только при устойчивой положительной пользе после затрат; иначе — no-action или `unavailable`. ML-классификатор риска и сложная оптимизация допустимы лишь при необходимых метках и доказанном преимуществе.

## 7. Serving и жизненный цикл модели

`Feature snapshot → champion models → batch inference → schema/quality gate → versioned forecast table → risk engine → optimizer → serving`. Обучение/переобучение не запускается из HTTP-запроса. Fallback: сезонная модель; если нет валидных входов — статус `unavailable`, не вымышленное число.

В целевом жизненном цикле F7 champion фиксируется в MLflow Registry после независимой shadow-проверки и утверждения, с возможностью возврата предыдущей версии; исследовательские запуски не меняют активную модель. Отдельно маркировать исторически опубликованный факт, актуальный GBFS, прогноз и сценарную рекомендацию. В реальном времени accuracy неизвестна до публикации actual: сначала контролируются свежесть, coverage, as-of/parity и технические ошибки, затем — поздние MAE/bias и сегментные деградации; невалидные данные блокируют публикацию.
