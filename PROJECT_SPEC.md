# PROJECT_SPEC — продукт и границы проекта

**Продукт:** BikeFlow Intelligence (независимый исследовательский проект на публичных данных Citi Bike).  
**Назначение:** единый источник продуктовых требований. Реализация — [ARCHITECTURE.md](ARCHITECTURE.md), формулы — [METRICS.md](METRICS.md), этапы — [ROADMAP.md](ROADMAP.md).

## 1. Зачем создаём продукт

Создать аналитическую и прогнозно-рекомендательную платформу для городского велопроката, которая помогает: (а) объяснять динамику поездок, (б) оценивать будущую нагрузку станций, (в) выявлять риск дефицита велосипедов/свободных доков, (г) сравнивать сценарии перераспределения. Ценность показываем через проверяемые показатели и честные симуляции, не через обещания экономии.

**Пользователи и решения**

| Пользователь | Решение, которое должна поддержать система |
|---|---|
| Руководитель | Где ухудшаются доступность и активность; как меняется ситуация |
| Аналитик | Какие факторы, сегменты, часы, станции объясняют изменения |
| Операционная команда (симулируемая) | Какие станции требуют проверки и какие перемещения теоретически полезны |
| ML-инженер | Насколько прогнозы надёжны; что влияет на ошибки и деградацию |

## 2. Функциональные требования

- **Историческая аналитика:** динамика поездок, отправления/прибытия, часы пик, районы, маршруты, категории; проверяемые гипотезы, сегменты и объяснения закономерностей, корректные сравнения и фильтры.
- **Мониторинг сети:** карта станций, доступные велосипеды/доки, статус работы, свежесть GBFS; пропуски не подменять нулями.
- **ML:** отдельные прогнозы отправлений и прибытий по станции и часу на следующие 24 часа; сравнение с простыми методами, диагностика ошибок, сохранение версий и интервалов неопределённости после калибровки.
- **Риски:** вероятность/оценка опустошения или переполнения станции, с указанием горизонта, неопределённости и методики.
- **Рекомендации:** сравнение «ничего не делать», простой эвристики и ограниченной оптимизации; сценарные допущения показывать явно.
- **Эксплуатация:** автоматическая поставка данных и прогнозов, проверки, мониторинг, откат, воспроизводимость.

**Новые ML-задачи:** добавляются только при отдельном полезном решении, подходящих данных и измеримом преимуществе перед простым методом. Симуляция и оптимизация не требуют отдельной обучаемой модели.

## 3. Чего не утверждаем

- Публичная история поездок отражает **опубликованные совершённые поездки**, не скрытый неудовлетворённый спрос. Сотруднические, тестовые и короткие поездки уже фильтруются источником.
- GBFS — текущие/периодически обновляемые состояния, а не архив прошлого. Исторический ряд формируется только с момента нашего собственного сбора.
- У нас нет полной информации о реальном парке грузовиков, сотрудниках, стоимости перевоза и скрытом спросе. Рекомендации — **симуляция**, не оперативные распоряжения Citi Bike.
- Выручка/прибыль не вычисляются напрямую по числу поездок. Для финансовых оценок потребуются дополнительные данные и проверенные допущения.
- Проект не связан с оператором Citi Bike; использование данных и бренда подчиняется их политике. Подробности: [knowledge_base/01_SOURCES_RESEARCH.md](knowledge_base/01_SOURCES_RESEARCH.md).

## 4. Обязательные свойства продукта

1. **Достоверность:** источник, временное окно, определение метрики и свежесть доступны пользователю.
2. **Воспроизводимость:** можно повторить исходные расчёты, эксперимент и публикацию конкретной версии.
3. **Отсутствие утечки будущего:** ML получает только доступную на момент прогнозирования информацию.
4. **Скорость:** тяжёлые расчёты и обучение вынесены из пользовательского запроса.
5. **Прозрачность:** отдельно помечены факты, прогнозы и результаты симуляции.
6. **Практичность:** измеряем производительность, не внедряем Kafka/Spark/Kubernetes без доказанной потребности.

**Начальные цели (не измеренные SLA):** p95 типовых API-запросов ≤300 мс; стартовый экран ≤3 с при определённой тестовой среде; ежедневный batch inference ≤5 минут. После нагрузочного профилирования цели либо подтверждаются, либо корректируются с объяснением. Без фактических тестов выполнение не заявлять.

## 5. Границы первого рабочего выпуска

**Первый вертикальный срез:** один полный архивный период → оригинальный файл → проверка → Parquet Silver → почасовой Gold → PostgreSQL → FastAPI → экран с реальными значениями. Для численно оцениваемого baseline потребуются отдельные исторические периоды обучения и тестирования.

**Вне первого выпуска:** полноценный многолетний EDA, нейросетевые эксперименты, сложная оптимизация, распределённый кластер, 24/7 high availability. Эти возможности идут после доказанного End-to-End (см. [ROADMAP.md](ROADMAP.md)).

## 6. Критерий принятия конечного продукта

- Непрерывная трасса от входных файлов до показателей дашборда; независимая сверка ключевых чисел.
- Полные data-quality отчёты, зафиксированные исключения и проверенные временные правила.
- ML-кандидаты оценены относительно обоснованного baseline на независимых временных периодах; улучшение и ограничения подтверждены по значимым сегментам, неподтверждённый кандидат не подменяет безопасный baseline.
- Симуляция риска и оптимизация сравниваются с простыми альтернативами; ограничения явны.
- Развёртывание повторяемо, API и UI протестированы, резервные копии восстановлены на тесте.

**Главный критерий:** продукт полезен как честная система поддержки решений даже тогда, когда прогноз неопределён или данные устарели.
